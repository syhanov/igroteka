# Design Note M06: Управление состоянием каталога

## Статус

Принято.

## Контекст

Для фильтрации и сортировки каталога можно каждый раз считывать значения непосредственно из полей формы либо хранить текущие параметры в отдельном объекте состояния.

В процессе разработки я столкнулся с трудностями при использовании первого варианта: сортировка работала некорректно до первого запуска отбора, а при повторной перерисовке каталога выбранная сортировка сбрасывалась.

## Решение

Для управления каталогом выбран отдельный объект `state`, содержащий текущие параметры поиска, фильтрации и сортировки.

Объект хранит значения `query`, `genre`, `platform` и `sort`. Функция `selectGames(GAMES, state)` использует эти значения для вычисления результата, после чего каталог отображается на основе полученного массива.

Такой подход выбран потому, что позволяет хранить настройки каталога в одном месте и отделить вычисление результата от чтения полей формы и отрисовки HTML.

## Рассмотренная альтернатива

### Чтение полей формы при каждом отборе

Этот вариант был отклонён из-за возникших трудностей с согласованной работой фильтров и сортировки. В частности, сортировка работала некорректно до первого запуска отбора и сбрасывалась при повторной перерисовке каталога.

Использование отдельного объекта состояния позволяет явно хранить выбранные параметры и применять их при каждом вычислении результата.

## Синхронизация состояния

При запуске страницы необходимо согласовать поля формы, объект `state` и отображаемый каталог. Если параметры переданы через URL, их необходимо учитывать при инициализации состояния и формы.

При сбросе фильтров необходимо вернуть значения `state` к настройкам по умолчанию, сбросить соответствующие поля формы и заново вычислить и отобразить каталог.

Это позволяет избежать ситуации, когда значения формы не соответствуют фактически применённым фильтрам или сортировке.

## Когда вариант без отдельного состояния был бы проще

Чтение полей формы непосредственно при отборе было бы проще для небольшого каталога с несколькими независимыми фильтрами, если бы не требовалось сохранять параметры между операциями или синхронизировать их с URL.

В таком случае отдельный объект состояния мог бы создавать дополнительную сложность без существенной пользы.

## Последствия

### Положительные

- параметры каталога хранятся в одном объекте;
- фильтрация и сортировка используют единый набор настроек;
- вычисление результата отделено от чтения формы и отрисовки;
- проще согласовывать состояние при запуске страницы и сбросе фильтров.

### Отрицательные

- необходимо явно синхронизировать состояние, поля формы и отображаемый каталог;
- при добавлении новых фильтров нужно расширять объект `state` и учитывать новые параметры при инициализации и сбросе.
